## Runtime architecture and file map

Root index.html loads catalog → state → rewards → economy → dialogs → scene → menu → worksheet-bridge → main. Function declarations can be replaced by later scripts; this is already happening with renderWorksheet.

## Complete gameplay and data flow

1. Boot reads panaderyaQuestV2, or fresh() starts with 250 coins, one Level-1 Pandesal, four menu slots, Normal mode and tutorial/sounds on. Refill creates a three-ticket board; render builds the menu between bakery navigation and tickets. First-use onboarding opens after 400 ms.
2. Ticket rarity is weighted within a cap derived from completion count and mastery. Permanent Luck biases higher grades. At mastery 12/24/40, Common/Uncommon/Rare weights respectively become zero. Grades generate 2×1, 2×2, 2×2, 3×2, 3×2 and 4×2 digit dimensions. Base budget is round((70 + 30 × digit-pairs) × (1 + rarity × .6)). There is no independent difficulty/carry-demand assessment.
3. startTicket removes the chosen ticket, immediately refills the board, calculates parent digit-pair steps and freezes a budget using current bakery value and mode multiplier. g.run holds ticket, aggregate progress, pool/luck/chests/error counters and bridge tracking; phase starts as engine. Actual worksheet state is separate inside the iframe.
4. Root render inserts worksheetFrame. On ready the shell sends start(ticket), sound(enabled), tutorial(enabled). Source markers are bc-shell into the iframe and pq-worksheet back. Child externalStart validates positive integer operands up to 99999 × 99, drives custom-number controls and resets worksheet/metrics.
5. The learner connects the current bottom and top digit in either tap order or by dragging. Only current pair indices are accepted. A capsule marks the connection; product phase shows a clickable M × N expression. revealProduct exposes ones and optional tens, preserving ones alignment within container bounds.
6. Place ones in the current shifted partial row. Tens can go directly to the next carry shelf, or temporarily into the row and then be lifted. Final multiplicand-column tens remain in the row. An incoming carry requires explicit source selection and a valid floating/placed ones target; adding it recalculates already placed provisional digits and outgoing carry. maybeAdvance blocks until incoming carry is merged, ones placed, and required outgoing tens resolved.
7. Combo completion advances right-to-left, resets carries between multiplier rows and prepopulates positional zeros. One-row problems finish immediately; two-row problems enter sum. A downward swipe triggers calculated right-to-left addition, visually merges rows, and raises the result. finish verifies the reconstructed answer equals a × b before marking complete. Example 79 × 18 follows 72 → carry 7, 56 + 7 → 63, yielding 632; the next row is 790; final addition is 1422. This sequence was inspected, not completed through browser gestures during this audit.
8. Every 180 ms bridgePoll emits changed state (stage, done count, carries, errors, combo metrics), completion once, and height when changed sufficiently. The parent interprets stage/carry changes as action rewards and increasing done as chest opportunities; it updates pool DOM without normally rerendering the iframe.
9. earnCoin caps action coins at floor(76% of budget). Its unit scales with parent step count and later row; necessary-action tracking is inferred from snapshots, not explicit action IDs. Temporary Luck increases, and chest chance is clamp(.12 + luck × .013 + row × .03, .06, .83). Drops reduce luck to round(30%). Final combo guarantees a chest if none exists; complete also has a fallback guarantee. Chest grade distribution depends on ticket rarity, not Permanent Luck.
10. Child complete triggers parent finishSum. Pool becomes the full frozen budget, adjusted for Bullseye accuracy or Streak best streak, and root rerender replaces iframe with a claim screen. Coins are not wallet funds before claiming. Abandon discards the pending pool/chests.
11. prizeItems adds coins, randomly chooses one food of each chest grade, creates owned copies and discovery entries, and autoassigns distinct foods if slots permit. It increments completed/learning/mastery, recalculates Permanent Luck, clears g.run, saves and shows the results. Clearing run guards ordinary repeated claim clicks.
12. Collection/upgrades change future ticket earning power: active menu food values, global kitchen bonus, and decor multiplier. Staff is independent elapsed-time coin accrual and never grants chests/mastery.

## Economy and progression actually implemented

- Individual food value = base × (1 + .20 × (level − 1)) × [1, 1.6, 2.5, 4][fusion]. Level cap 3; fusion cap 3.
- foodSum counts only the strongest active copy of each food ID. Bakery value = max(1, foodSum) × kitchenBonus × decorBonus. Duplicate active slots therefore do not necessarily add value.
- Kitchen adds global percentage bonuses by item level (cap 5). Decor multipliers are 1, 1.08, 1.19, 1.35, 1.55. These are implementation numbers, not validated balance.
- Duplicate fusion consumes the first other matching owned copy and a fee, retaining target level and adding donor spent to target spent. Ingredient fusion pays missing fixed-price ingredients plus the same fee and consumes stock.
- Whole-item resale = round(food base × 45) + floor(spent / 2); removes active assignment but preserves discovery. The base formula is an unresolved design choice.
- Slot price starts 420 and grows ×1.9 per purchased slot beyond four. No explicit slot cap.
- Kitchen opens after 2 claimed orders, challenges begin at 3, decor at 4, fusion/shop nominally at 5, staff at 6. All systems remain discoverable through nav/dialogs; not a fully designed contextual feature introduction.
- Staff shift lasts 120 s, rate max(.4, bakeryValue × .76), upfront fee ceil(rate × 36), with elapsed-time/fraction accounting. Active ≥3× passive is only a target: no solving-pace measurement or timing normalization validates it. For Common Normal tickets, gross active/passive ≥3 requires roughly ≤57 s per order; net staff comparisons depend on whether hiring cost is counted.
- Error-free Normal/Lookup claims add one mastery; challenge claims add two. Otherwise ≥90% counted correctness adds one. Permanent Luck is floor(mastery/4). No retention tests, carry/alignment competency model or deliberate practice revisit selector exists.

## Findings, ordered by priority

Evidence labels: **source-confirmed** means directly established by executable paths/conditions; **VM-confirmed** means a small in-memory Node check was also run; **browser verification needed** marks effects depending on real rendering/input/timing. These are not claims of completed device testing.

### P1 — session integrity, learning and reward correctness

1. **Worksheet progress is lost on parent rerender (source-confirmed).** main.render replaces app.innerHTML and creates a fresh iframe. closeModal always calls render, including closing Help/Settings/Chances mid-problem. Reload likewise restores g.run aggregates but not child s/history. ready/start resets the problem; started resets bridgeDone/signature but leaves prior pool/chests/mistakes/bridgePrev. Save messaging implies more resumability than exists. Repro to verify: solve a combo, open/close Help, inspect worksheet and pending counters.
2. **No durable unique-action reward ledger (source-confirmed architecture risk).** Parent rewards changed stages/carry counters; undo restores worksheet math but not bridgeMetrics carry/error counters or parent rewards. Repeating reveal/undo can alternate fact/place stages and add Luck/coins; replaying completed work after a frame reset can add chest opportunities because bridgeDone resets while chests persist. Coin pool is capped and final payout overwritten by budget, so this is not unlimited immediate wallet coins; Luck/chests/accuracy evidence remain vulnerable. Completion count monotonic tracking limits some ordinary undo repeats within one child session, but does not solve resets. A stable run/session/action identity is needed before claiming farming prevention.
3. **Mode descriptions exceed active implementation (source-confirmed).** The effective iframe receives operands/sound/tutorial, not mode rules. Lookup table and recall-input challenge are in the overridden root renderer; Lookup has no active table and Blindfold does not enforce recall. Streak/Bullseye bonuses apply to broadly the same interaction; mistakes are invalid gestures/placement, not assessed independent facts. Challenge mastery can be doubled without added demonstrated skill.
4. **Survival differs from the stated rules (source-confirmed).** Bridge path computes livesLeft = g.lives − floor(mistakes/2), meaning two errors per life, while the legacy path uses one per error. Wrong pair/placement and some pointer slips increment invalid/errors. Failed retry resets several aggregates but not bestStreak/streak/livesLeft/bridgeErrors; a new child session may hide some stale fields. Lives selector is only in unmounted renderModePanel, so the normal UI offers no 1/3/5 selection despite claiming it does.
5. **Tutorial OFF leaves addition guidance (source-confirmed).** embedded-controls.js correctly receives tutorial messages; main tutorial stream checks tutorial, but updateAdditionSwipeGuide does not. Separate additionSwipeGuide layer remains populated at sum; toggling calls positionFloater without clearing that layer. Architecture doc's suspected missing command handler is therefore stale; the narrower guide bug remains.
6. **Polling loses and misattributes meaningful actions (source-confirmed risk, timing verification needed).** At 180 ms several actions can collapse into one report. Parent signature omits some child metrics. r.correct counts roughly two per newly observed completed combo plus completion, not all unique correct actions; accuracy is not a calibrated learning measure. Parent earnCoin uses previous r.index before updating from m.done, potentially misweighting row transitions. Rewards derive from UI stages rather than domain events.

### P2 — economy, feature access and persistence

7. **Ingredient investment is understated (VM-confirmed).** Shop purchases deduct coins without tracking cost basis on stock/food. fuseIngredients adds only current fee and missing purchases to spent; previously bought ingredients consumed are unrecorded. Example: prebuy 2 Flour + 1 Yeast for 60, fuse Pandesal with fee 190: spent is 190, not 250. Later resale misses 30 refund coins. No changes made.
8. **Duplicate slot presentation disagrees with value (VM-confirmed).** A second active Level-1 Pandesal still yields foodSum 1.2. chooseFoodForSlot offers other copies and says each adds value; assignFood lacks already-assigned UID guard. Decide/document intended distinct-food rule before altering balance.
9. **Fusion unlock can be bypassed through regular UI (source-confirmed).** openFoodItem disables fusion before five orders, but openMenu renders duplicate/ingredient fusion buttons without the completion gate. ingredientFusionInfo/fuseDuplicate/fuseIngredients also do not enforce it. Pre-five duplicate drops can expose this discrepancy.
10. **Save validation and error visibility are weak (source-confirmed).** Only a few fields are defaulted; missing nested arrays/learning/staff fields, invalid food IDs or out-of-range values can break later paths. save silently ignores storage failures. JSON serializes Infinity retries as null; treat finite/infinite retry policy deliberately if restoring runs. Keep panaderyaQuestV2 unchanged; any schema change needs tested migration.
11. **Decor evolves the wrapper, not worksheet internals (source-confirmed).** No renovation state is sent into iframe. Actual receipt skin stays fixed; theme is clamped to 3 even at decor 4, making .worksheet-stage.theme4 unreachable. Dialog promises overstate implementation.
12. **Mastery/practice claims are ahead of design (source-confirmed).** Count/error-derived mastery removes easier rarity tickets without retention evidence. Modes explanation mentions easier practice revisits, but no practice selection UI exists. Rarity also changes difficulty, so collection opportunity and learning class are coupled.
13. **Staff balance and display need validation.** No pace data establishes ≥3× active advantage. When staff is running, dialog displays recalculated staffRate rather than the hired fixed g.staff.rate, so upgrades can make displayed rate differ from actual earnings. Timer correctly accrues only until shift end and can catch up elapsed time on reload.
14. **Music preference does not resume on boot (source-confirmed).** musicOn is loaded but bootstrap does not start music. Browser activation policy needs consideration. Music error handling sets g.sound=false, mixing separate preferences. Sound volume sent over bridge is ignored; enabled flag is handled.

### P2/P3 — architecture, styling, accessibility and maintenance

15. **Competing worksheet systems and ambient globals.** scene.js defines renderWorksheet, then worksheet-bridge.js overrides it. Legacy action handlers/reward paths remain callable; refactoring order can accidentally reactivate old behavior. Many DOM-inline handlers, global bindings and cross-file dependencies make isolated changes fragile. Bridge monkey-patches math functions for telemetry, coupling instrumentation to validation/animation timing.
16. **Protocol validation is incomplete.** Parent checks ev.source against current iframe and marker, but not origin/ticket ID/run nonce. Child checks only marker, not event.source or origin. Both post to '*'; parent complete does not verify supplied ticket/operands/stats against active run. This is a local static prototype trust boundary, not a claim of a demonstrated remote exploit. Same-origin sandboxed iframe is not a security boundary against its own scripts.
17. **Styles contain HTML fragments (source-confirmed).** effects-and-guides.css ends with '<style>'; receipt-theme.css ends with '<style>.addition-lab,.multiplication-lab{...}'. External CSS does not parse this as an HTML style element. The first malformed selector/rule is unreliable; later rules may recover. Hidden lab visibility needs browser confirmation. Do not claim the intended hiding rule works because text exists in a file.
18. **Standalone manual testing instructions are misleading.** embedded-layout.css unconditionally hides .top (custom operands/sound/tutorial/restart), and foundation hides settings/footnotes. Opening worksheet directly does not expose the documented custom controls. An exposed debug API exists, but is not a child-friendly practice UI.
19. **Unused experiments/cascade complexity.** Hidden visual/multiplication lab controls, array animation helpers and historical overrides remain despite preferred M × N flow. Several visual skins and responsive breakpoints stack across files; preserve current behavior with screenshots before consolidating. No appearance change is recommended without separate approval.
20. **Accessibility/device risks require hands-on review.** Root viewport disables user scaling; modal lacks focus trapping/restore and Escape handling; drag logic has no keyboard equivalent for every gesture; button exclusion in addition-swipe start means a swipe beginning directly on digit cells does not start addition. There is no visible active merge button in the effective shell. Narrow worksheets can scroll under absolute overlays; iframe height is clamped to 570–1030 while child height is content-based, risking nested scroll or clipping. These layout/gesture effects were not browser-tested here.
21. **Worksheet reset leaves cosmetic completion remnants.** reset clears complete contents and state but not receipt stamp/cash-terminal classes/machine text, so standalone restart/undo can leave stale completion decoration. Main claim normally removes the iframe quickly, limiting visibility.
22. **Tests are structurally useful but shallow.** Per-file parsing does not detect global-name collisions across concatenated classic scripts. Regex/presence tests do not prove mathematical correctness, valid DOM selectors, actual CSS parsing, message ordering, mode enforcement, save round-trips or unique rewards.
